# 项目重点与内核

## 一句话内核

把家庭工程隐患从“看不见、说不清、验不了”，变成“可读数、可判断、可执行、可复测”的闭环。三维游戏是载体，真正的主体是**工程知识**与**过程数据**两条闭环。

## 两条闭环

### 1. 数据闭环

传感器采集 → 阈值分级 → 持续确认 → 生成报警证据 → 自动派单 → 现场处置 → 读数回落 → 观察期 → 闭环验收或重新打开。

关键点不是“有数据”，而是数据同时承担三种作用：

- 报警前：作为判定依据，排除正常波动与瞬时干扰；
- 处置中：作为工单证据，记录触发值、时间、位置与级别；
- 处置后：作为验收判据，读数未回落并持续正常，工单不得关闭。

### 2. 知识闭环

现场现象 → 成因诊断 → 按真实顺序执行工序 → 危险操作触发事故 → 记入已掌握 → 手册对应条目打勾。

关键点不是“有手册”，而是手册内容被做成必须判断、必须排序、必须承担后果的交互环节。玩家完成一次处置，同时获得一套可迁移到真实家庭问题的处理流程。

## 三类用户与信息深度

| 用户 | 关心什么 | 系统应提供 |
|---|---|---|
| 施工方 | 哪里异常、先做什么、用什么工具、多少钱 | 原始读数、阈值、工序、安全前置、分项费用 |
| 居民 | 哪些问题还没消除、影响哪些区域、大概多少钱 | 未消除项、影响范围、预算、可自修与须物业的界限 |
| 验收方 | 施工方说修好了，依据是什么 | 原始读数、触发证据、处置记录、复测结果、闭环判据 |

三类用户共用一套数据，但信息深度必须不同。这是“场景与用户”评分项的核心，不是界面装饰。

## 项目重点：答辩时必须让评委看到什么

### 重点一：不是“点一下修好”

处置环节要求先由现象与读数反推成因，再按真实作业顺序执行工序。顺序错误返工，点到危险操作触发事故并赔付。

### 重点二：不是“见峰就报”

单点越限不报警，必须连续超阈值达到确认时长；瞬时尖峰被标为干扰并抑制，避免正常波动造成误报。

### 重点三：不是“修完即验收”

工单完工只进入观察期。读数未回落、未持续正常，工单不得判为已验收，可重新打开。

### 重点四：不是“只有一条费用”

已有材料、人工、管理费分项核算。下一步必须补两种整改组合与 8000 元预算约束，才能完整对应“整改决策”20 分。

### 重点五：不是“只有一个用户视角”

施工方看读数与工序，居民看未消除项与预算，验收方看原始证据与复测。当前数据已经具备，下一步补界面视图切换。

## 答辩金句

- 我们不是把维修做成点击动画，而是把工程知识做成必须判断、必须按序执行的交互。
- 报警不是单点峰值，而是持续确认后的证据。
- 验收不是施工方说修好了，而是读数回落并持续正常。
- 游戏是载体，能力转移是目的。

## 现场证据清单

- 监测平台：点位、读数、阈值、报警状态、派单日志。
- 工单链路：待维修、维修中、已完工、观察期、已闭环、重新打开。
- 处置交互：诊断选项、工序排序、危险操作事故、已掌握清单。
- 手册：当前工单工序与维修面板完全一致。
- 费用：材料、人工、管理分项；方案 A/B 与预算（补齐后）。
- 简报：异常证据、处理记录、费用、复测结论。
- 离线：断网冷启动并完成全流程。
